      What the words mean

      Matched call
      A request and its reply are both in this capture. They share a TCP stream and the same opaque, the client’s semi-transaction number for that one call.
      Opaque
      The semi-transaction number on a Couchbase request. The matching response repeats it. In Wireshark, filter tcp.stream and couchbase.opaque together to see that pair. The same opaque on a different stream is a different call. A Statistics request sends many response packets on that one opaque, one stat line each, and they count as one call. On DCP the stream request chooses the opaque, and every later snapshot and mutation on that stream copies it. Those packets do not expect a command reply unless the snapshot ack flag is set. A later packet is the next change, not a retry.
      Stream
      The TCP connection number Wireshark assigns. Opaque is only unique inside one stream. The same opaque on stream 0 and stream 1 is two calls.
      Left
      Seconds of capture still remaining after this packet. A small Left means the file was about to end. A request with a large Left had time for a reply to appear.
      Where
      Inside means the packet is outside the in-flight window at the open or the close of the file. End of file means the request is still inside the longest completed round trip of the close, so a missing reply can be the capture stopping. Start of file means the reply is inside that window of the opening, so the request may have been sent before recording started.
      Lost response
      The request is in the file and the reply is not. That happens when the recording stops while the call is still open, or when the reply packet was never captured. A cell that says not expected is a command that does not want a reply.
      Not expected 1

      The Lost responses column counts a missing command reply, magic 0x81 or 0x18. Not expected means this command does not want that reply, and none of these packets were left waiting for one.

      A DCP mutation (0x57) is pushed by the producer. The consumer does not send a command reply. Flow control is a later buffer acknowledgement (0x5d). Opaque 0 on that acknowledgement covers the whole connection. A mutation with no 0x81 is the normal stream.

      A snapshot marker (0x56) wants a reply only when the snapshot flag 0x08 (Ack) is set. When that bit is clear, the marker starts the snapshot and the mutations after it are the documents. They share the stream opaque, and that number is the stream id. A marker with the ack flag set is an ordinary call, so a missing reply shows as a number in this column.

      Stream end (0x55), deletion (0x58), expiration (0x59), and the buffer acknowledgement are one-way in the same way. A DCP noop (0x5c) does want a reply: the producer drops the connection if the consumer stays silent. A stream request, Set with Meta, Get Meta, and a Statistics poll such as vbucket-seqno also want a reply. A missing one shows as a number.

      Slow-call scatter
      Each dot is one matched call that took 50 ms or more, up to the slowest 2,000. Horizontal is when the request started. Vertical is the round trip. Blue is an application call. Rust is cluster replication. A p99 line can be three calls or a cloud of them. The dots show which. A vertical stack is many slow calls in the same moment.
      Server time
      Choose “server time against round trip” on the slow-call chart. Horizontal is couchbase.flex_frame.frame.duration, the microseconds the server held the command from receive to send. Vertical is the round trip in milliseconds. A dot near the diagonal means the server was doing the work. A dot high and to the left was waiting outside the server: the network, the client, or a durability hold. The chart keeps the slowest calls that reported a duration and a spread of the others, about 2,000 dots. An empty chart means this capture did not report that flex frame. That is “not reported,” not a duration of zero. Wireshark 4.6 prints the field in microseconds.
      Missing heatmap
      Each cell is one time bucket and one address, or one command. Color is how many requests in that cell have no reply. A vertical stripe means every listed row failed in that second. A horizontal stripe means one address or one command was missing the whole way across. The list is the addresses and commands with the most missing replies, up to 12. DCP commands that do not want a reply are not in this grid. They are not expected.
      Opcode box
      One box per command that got a reply, the slower tails first. The line in the middle of the box is the median. The box is the middle half of those calls, from p25 to p75. The whisker runs from the fastest call to p99, so one extreme call does not squash the rest. A short box with a long whisker is usually fast, with a thin slow tail. A tall box is usually slow. The p99 bar elsewhere is only the end of that whisker.
      Call flow
      Left is application or cluster. Middle is the command. Right is where the call went: matched, not found, key exists, an error status, a missing reply, or not expected. The width of a band is the count. Not found is status 0x0001, a normal Get. Key exists is status 0x0002, a conditional write that found the document already there. An error status is a reply such as not my vbucket, locked, busy, temporary failure, or rollback. Not expected is a DCP message that does not want a command reply. The middle keeps the eight busiest commands and folds the rest into Other.
      Reply status
      A bar for each Couchbase status on a reply that is not success. Success is left off so it does not hide the rest. Key not found and key exists are normal results, drawn in green. Not my vbucket, locked, busy, temporary failure, and rollback are drawn in rust. Not my vbucket means the client talked to the wrong node and will try again. Busy and temporary failure mean the server told the client to back off. Rollback means a DCP stream has to restart. A reply with one of those statuses is a matched call, so it is not in the missing-reply count.
      Durability
      Requests grouped by couchbase.flex_frame.frame.durability_req. Majority (0x01) is in memory on a majority of nodes, with no disk wait. Majority and persist on master (0x02) also waits for disk on the active node. Persist to majority (0x03) waits for disk on a majority. The bar is the p99 of calls at that level that got a reply. The two disk levels are the ones that stretch a Set while the server duration stays tiny. No durability means the request did not ask. An empty set of disk levels means this capture did not ask for them. When a reply carries time to replicate or time to persist, that estimate is how long the server said the durability step still needed.
      Time to replicate and persist

      couchbase.ttr is time to replicate. couchbase.ttp is time to persist. Wireshark prints both in milliseconds. They are the server’s estimate of how long until that step is done, not the round trip. Zero means the step is already done. A high time to replicate means the write is still waiting for a majority of nodes to hold it in memory. A high time to persist means it is still waiting for disk. Either one holds a durable write, which is why a Set can be slow while the server duration stays tiny.

      The solid lines are the median in each time bucket. The dashed lines are the p99. A bucket with no such field is blank. Wireshark writes these two numbers only on Observe (0x92). They replace the CAS field: the first four bytes are time to persist, the next four are time to replicate. A durable Set does not carry them. Its request carries the durability level, and the reply waits until that level is met.

      VBucket
      The vBuckets with the most missing replies, then the most calls over 100 ms. The number is couchbase.vbucket. One vBucket points at one active node or one replica. A spread across many vBuckets points at the client or the capture.
      Snapshot kind
      Each bar is a DCP snapshot marker (0x56). Memory (couchbase.extras.flags.dcp_snapshot_marker_memory) is steady replication. Disk (couchbase.extras.flags.dcp_snapshot_marker_disk) is a backfill from disk. A marker with both bits counts as disk. The line is the widest sequence span in that bucket, end seqno minus start seqno. A span of 0 is a snapshot of one sequence. A disk marker with a wide span is catch-up, not an application slowdown.
      Buffer acknowledgement
      The bars are DCP mutations (0x57). The line is the bytes the consumer gave back with a buffer acknowledgement (0x5d, couchbase.extras.bytes_to_ack). Opaque 0 on that acknowledgement covers the whole connection. Mutations while the credit line is on the floor means the consumer is not keeping up. That is flow control. It is not a missing command reply.
      Response without request
      The reply is in the file and the request is not. The request was usually sent before the recording started. Extra packets from a Statistics reply are not this: they repeat the opaque on purpose and stay with that request.
      Response time
      Milliseconds from the request packet to the matching reply. Only matched calls have one.
      Latency band
      A slice of response time, such as 30–40 ms. The histogram counts how many matched calls finished in each slice.
      Median, p90, p95, p99
      The median is the middle call. p90 means 90 percent of matched calls were that fast or faster. p99 is the slow end: only 1 percent were slower.
      Opcode
      The kind of Couchbase operation, such as Get or Set. The opcode table lists the hex code and what each command in this capture does.
      Document id
      The Couchbase key the operation named.
      Total body length
      Bytes of extras, key, and value in one Couchbase packet. Into Couchbase is the request. Out of Couchbase is the reply. 1 MB is 1,048,576 bytes.
      NIC headroom
      The gauge uses the selected time bucket. For each bucket it adds document bytes in and document bytes out, then takes the busiest bucket and turns that sum into a rate. The needle is that rate. The scale ends at 10 Gbit, which is 1,250 MB/s. The color changes at 1 Gbit, which is 125 MB/s. Green is under a 1 Gbit NIC. Gold is between 1 Gbit and 10 Gbit. If the busiest bucket is past 10 Gbit, the scale grows and the extra range is red. These are Couchbase body bytes, extras plus key plus value, so the NIC carried the frames around them as well. A needle past a mark means the documents alone filled that pipe. A needle sitting in the green means document size was not filling a 1 Gbit NIC in that bucket.
      TCP loss
      A hole in the recorded TCP byte stream. Toward the client means the server’s packets are missing, often the reply. Toward the server means the client’s packets are missing, often the request.
      Retry
      The sender transmitted the same TCP data again after waiting out a timeout. A second copy that arrives within a millisecond is a capture duplicate, not a retry.
      Capture duplicate
      Wireshark marks a second copy of the same TCP segment as a retransmission. When that copy arrives within a millisecond, TCP did not retry. The segment was recorded twice, often because the capture saw the packet on the way in and on the way out. The payload is frequently the middle of a document, not a new Couchbase command, and it is not a DCP retry. The bar on Packets on port 11210 starts hidden. Click Capture duplicate in that chart’s legend to show it. A red Retransmission bar is a resend that waited out a timeout.

      What each chart is for

      1. How long calls took shows whether slowness is a few calls or the usual case. A tall bar on the right is a slow tail.
      2. Calls by opcode and response time lines up a burst of one operation, such as Get, with the median and p99 in that same moment.
      3. Round trip follows the typical call and the slow tail across the capture. The crosshair is the same moment on every time chart.
      4. Latency range shows the spread in each bucket. The thick part is median to p90. The thin line is the fastest call to the slowest.
      5. Lost responses, retries, and TCP loss shows missing Couchbase replies next to holes and resent TCP data. Loss toward the client lines up with a missing reply. Loss toward the server lines up with a reply whose request is missing.
      6. Clients is which machines sent the operations, as a fleet and one address at a time. p99 by opcode is which kind of operation has the slow tail.
      7. Packets on port 11210 is a bar for each Couchbase command, split into request and response. Capture duplicate, TCP data, and TCP ACK start hidden.
      8. Total body length uses bars for the largest request and the largest reply, and dashed lines for every document byte in that second. A high bar is one large document. A high line is a busy second. A 1 Gbit NIC carries about 125 MB/s, and a 10 Gbit NIC about 1,250 MB/s.
      9. The tables are the busiest document ids, and the ten slowest matched calls. Set Stake on a slow call marks that second on the time charts, including the body-length chart.
      10. Diagnosis is the scatter, heatmap, box, and flow for slowness, missing replies, and odd statuses. Each chart links to its reading above.

      Data source

      The charts and tables on this page are drawn from charts.json. Python writes that file before a model runs. tshark reads the packets whose source or destination is TCP port 11210. A call is one TCP stream plus the Couchbase opaque. The file holds the capture length, the server address, half-, one-, five-, and ten-second buckets, percentiles, opcodes, body sizes, TCP loss in each direction, client connections, the busiest document ids, the ten slowest calls, a sample of missing requests and replies with the full counts, the points of interest, and the next questions. When a model runs, it writes summary.md from these counts. It does not change this file. facts.json beside it is the same counts in the shape the note uses.
